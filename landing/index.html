El ciclo Scrum de Fluxo

Un método vivo, no un PDF de proceso.

Cada estación de este diagrama es real y observable en tiempo real: naranja = hecho o activo, azul punteado = aún no corrido, ◆ ámbar = gate esperando tu decisión. El humano decide en los rombos; el motor hace el resto — sin quitarte el control en ningún punto.

Cómo funciona

Seis fases gateadas. Cada una la firmás vos (o tu cliente).

El brief entra por un lado; salen Issues de GitHub con dependencias nativas por el otro. En cada fase hay un ◆ gate: aprobás, corregís, o respondés las preguntas abiertas de esa fase.

◆
01

Discovery

Brief vago en español → alcance, supuestos y preguntas abiertas resueltas contigo.

◆
02

PRD + data-model

El QUÉ antes del CÓMO: requisitos y modelo de datos con dueños de transición server-side.

◆
03

Arquitectura

Estructura, límites de paquetes, presupuestos de performance, contrato de provisioning.

◆
04

UI + mockups

Pantallas descritas + un mockup HTML navegable que el cliente clickea y aprueba.

◆
05

Backlog

Épicas → sprints → stories con criterios de aceptación y un grafo de dependencias.

◆
06

Handoff

Publica Issues en el repo del cliente con el grafo blocked_by nativo.

brief → discovery → PRD → arquitectura → UI → backlog → GitHub Issues + deps → ejecución gobernada (Copilot o Claude, tu decidís) → Pull Requests trazables
Por qué no es "otra herramienta de specs"

El artefacto es una commodity. La gobernanza es el producto.

Generar un spec o un backlog hoy es gratis (Spec Kit) y ejecutar agentes multi-modelo viene incluido en tu Copilot. No competimos ahí. Lo que una agencia le cobra a un cliente es lo que esas herramientas no te dan: un plano de control gobernado y un entregable que el cliente firma.

Commodity · gratis / incluido

Generar specs y correr agentes

  • El artefacto de spec / backlog (Spec Kit lo da idéntico, gratis)
  • Ejecutar agentes multi-modelo en tu repo (Agent HQ, en tu Copilot)
  • Un CLI en el IDE de un dev, sin proceso ni trazabilidad
  • Ningún cliente-facing: nada que mostrarle ni firmar
El envoltorio que se cobra

Entrega gobernada, cliente-facing

  • Gates humanos como workflow — aprobar, corregir o responder, en cada fase
  • Trail requisito → issue → PR — un entregable auditable que le mostrás al cliente
  • Plano de control hosted, multi-proyecto — no un CLI per-dev en un IDE
  • Elicitación español-first — donde las tools GitHub-native subatienden
  • Sin lock-in del modelo — Copilot o Claude, la agencia elige por lane
El entregable que factura

Trazabilidad de punta a punta, en un solo hilo.

Cada línea de código llega a un PR; cada PR cierra un Issue; cada Issue nace de un requisito que el cliente aprobó. Ese hilo es lo que adjuntás a la factura y lo que gana la confianza del cliente.

Para quién es

Agencias y dev shops boutique de LATAM.

  • 1
    3–20 devs que entregan software a la medida a clientes externos de pago, sobre GitHub.
  • 2
    Que necesitan proceso y trazabilidad para ganar y retener la confianza del cliente — no solo escribir código.
  • 3
    Español-first, elicitando requisitos con clientes que hablan español.
  • 4
    Que ya viven en GitHub y quieren specs de calidad + ejecución gobernada sin atarse a un modelo.

No es para

  • El indie hacker / founder no-técnico "idea→app" — usá Lovable, Bolt o v0.
  • El dev solo que solo quiere mejores specs — Spec Kit es gratis en tu IDE.
  • El enterprise con procurement de 9 meses y SSO/SOC2 como requisito de entrada.

Preferimos decirte que no somos para vos hoy, a venderte un asiento que no vas a usar.

Precios

Por agencia, no por asiento.

No revendemos compute de ejecución (tu Copilot / tu Claude siguen siendo tuyos). Cobramos el método, la gobernanza y la trazabilidad. Solo los design-runs (nuestro único COGS real) se miden como overage.
