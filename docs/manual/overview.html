Una fábrica que convierte
ideas en software que se despliega

Fluxo toma una idea, la diseña fase por fase —con vos aprobando cada una—, la vuelve Pull Requests en GitHub que un agente de IA implementa y verifica corriendo la app de verdad, y los mergea. Este es el recorrido, de punta a punta.

idea→ diseño→ backlog→ PRs→ verificado→ mergeado
La mitad que decide

Studio · el diseño

Vos y los agentes definen qué construir, fase por fase. Vos aprobás cada gate. El resultado son documentos y un backlog. Acá vivís vos.

La mitad que trabaja

Conductor · la ejecución

El backlog se vuelve Issues de GitHub y el Conductor despacha el trabajo a un agente que abre PRs. Trabaja solo, sobre GitHub como fuente de verdad.

03

Ejecutar

El Conductor construye, solo, sobre GitHub.

Con la spec ya en main, el Conductor proyecta desde GitHub cada ~25s y mueve el trabajo hacia adelante. Un ciclo que se repite hasta terminar el backlog.

01 · despacha

Reparte

Calcula qué stories se pueden hacer (deps ok) y las manda a un canal: Copilot o Claude.

02 · implementa

Abre PRs

El agente escribe la story en una rama y abre el Pull Request.

03 · verifica

Chequea

Corren tests, lint de frontera y e2e contra un backend real.

04 · integra

Mergea

Auto-merge si es seguro; cierra el Issue y libera las stories que dependían.

04

Verificar

Prueba el comportamiento, no los artefactos.

Acá está la diferencia. La mayoría de los tests mockean la frontera con el sistema real — y ahí viven los bugs que llegan a producción. Fluxo tiene tres capas que atacan eso.

Capa 1 · estático

provisioning-lint

Lee el código real contra el contrato de frontera: ¿falta un índice para esta query?, ¿un permiso de plataforma?, ¿un rol sin declarar? Barato, sin backend.

Capa 2 · comportamiento

e2e-verify

Levanta el backend real (emulado), se registra como usuario, ejecuta el flujo y comprueba invariantes. Caza reglas que deniegan al cliente, funciones que crashean en cold-start, sesiones que no persisten.

Capa 3 · deploy

release-gate

En el despliegue confirma lo que solo se puede confirmar ahí: que el índice está construido, que los permisos están aplicados.

Un mismo motor genérico verifica Flutter + Firebase o React + Supabase — la diferencia vive en datos por-stack, no en el código. Agregar una plataforma es un archivo de contrato, no un refactor.

El ciclo completo

De la idea al merge, una vuelta

idea → diseñás 8 fases (aprobás cada gate) → spec a main → el Conductor despacha sprints → el agente abre PRs → verificación en 3 capas → merge → repetís la iteración
