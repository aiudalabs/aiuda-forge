Fluxo es una fábrica autónoma de software. Vos describís la idea; unos agentes de IA la diseñan fase por fase (vos aprobás cada una), la vuelven Pull Requests en GitHub, los verifican corriendo la app de verdad, y los mergean. Mínima intervención humana.

💡 idea→ 📐 diseño→ 🎫 backlog→ 🔀 PRs→ 🔬 verificado→ ✓ mergeado

La idea en una frase

Dos mitades: una diseña, la otra ejecuta

Todo lo que hace Fluxo cae en una de dos. Vos vivís en la primera (decisiones); la segunda trabaja sola sobre GitHub.

📐
Studio · el diseño

Vos + los agentes definen QUÉ construir

Fase por fase —descubrimiento, PRD, arquitectura, UI, mockups, backlog— y vos aprobás cada una en un gate. El resultado: documentos y un plan de trabajo.

🎼
Conductor · la ejecución

La IA lo construye sobre GitHub

El backlog se vuelve Issues; el Conductor despacha sprints a un agente (Copilot o Claude) que abre PRs, se verifican, y se mergean. GitHub es la verdad; Fluxo lo proyecta.

El ciclo · ejecución

El Conductor construye, solo

Con la spec en main, el Conductor proyecta desde GitHub cada ~25s y mueve el trabajo hacia adelante.

🧭

Despacha

Calcula qué stories se pueden hacer (deps ok) y las manda a un canal: Copilot o Claude.

🔀

Abre PRs

El agente implementa la story en una rama y abre el Pull Request.

🔬

Verifica

Corren los checks: tests, lint de frontera, y e2e contra un backend real.

✓

Mergea

Auto-merge si es seguro (o espera tu OK). Cierra el Issue y libera las que dependían.

La diferencia

Verifica el comportamiento, no los artefactos

La mayoría de los "tests" mockean la frontera con el sistema real — y ahí viven los bugs que llegan a producción. Fluxo tiene tres capas que atacan eso.

Capa 1 · estático

provisioning-lint

Lee el código real y lo contrasta con el contrato de frontera: ¿falta un índice para esta query?, ¿un permiso de plataforma?, ¿un rol no declarado? Barato, sin backend.

Capa 2 · comportamiento

e2e-verify

Levanta el backend real (emulado), se registra como usuario, ejecuta el flujo, y comprueba invariantes universales. Caza reglas que deniegan al cliente, funciones que crashean en cold-start, sesiones que no persisten.

Capa 3 · deploy

release-gate

En el despliegue confirma lo que solo se puede confirmar ahí: que el índice está construido, que los permisos están aplicados.

El diseño es agnóstico del stack: un mismo motor genérico verifica Flutter+Firebase o React+Supabase — la diferencia vive en datos por-stack, no en el código. Agregar una plataforma es un archivo de contrato, no un refactor.
